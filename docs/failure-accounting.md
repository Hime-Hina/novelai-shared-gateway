# 失败退款与资源核对的当前实现

本文件对应 F03 已实现的前两片：尝试证据、原资源退款、聚合资源差额与明确来源运营资金。五分钟自动结案、迟到证据/结果调整、管理页展示与告警仍在后续实施范围；不能据此宣称已经解决全部崩溃恢复。

## 三件事分开记录

- 成员本地预扣和退款：固定 Anlas、购买 Anlas、V5 分开；退款只退原预扣一次。`reserved` 到终态的持久状态迁移负责幂等，成功后的重复失败不退款。
- 上游消费证据：`generation_reserved` 在派发事务中保存尝试身份、操作、成员/账户、批次、本地原金额、候选资源和安全快照。实际失败后追加退款及疑似消费事件；报价不等于 NAI 实扣。本地 Anlas 续用的 V5/Anlas 是互斥候选，不能相加。
- 聚合来源差额：同步发现无法由已有结算抵消的 Anlas 下降时，保留成员权益，记录 `resource_gap_observed`，不按份额扣其他成员。记录只能说明聚合余额有缺口，不证明某一笔请求被收费。

V5 当前容量差额独立记录。整数官方快照保留一个百分点的精度边界，不把边界内的舍入误差认定为实扣。可信恢复速率产生的恢复先偿还原有续用估计负债，再抵消容量差额，剩余才分给尚未满额的成员。已有运营 V5 份额也计入总来源占用，不能因为转入运营钱包就再给成员恢复一份。恢复追加事件，不删除历史。

## 负差额、正向回跳与真正新增

普通没有未归属缺口的官方新增 Anlas 继续自动按既有份额分配，不要求每次充值/续订登记收据。明确登记为运营注资的新增先匹配收据，剩余才进入普通分配。

已有未确认的聚合负差额时，单次正差额可能是快照回跳，也可能是真实新充值。现有同步字段只有聚合余额，不能可靠区分，因此仅将可能对应缺口的部分记为 `unattributedReturns`，超出这部分的新增仍自动分配。待归属余额不是运营收入，不自动核销损耗，也不作为新的调用限制。

| 反例 | 处理 |
| --- | --- |
| 官方固定 10000 → 0 → 10000，缺少充值或快照纠正证据 | 成员仍保留原 10000 权益；保留 10000 未确认缺口及相应待归属返回，不把钱包变成 20000，也不宣称损耗已消失 |
| 有明确公共新增 1000 的唯一收据，同时还存在旧缺口 | 新 1000 照常按份额分给成员，旧待承担不变；不挪用成员新增自动填运营损耗 |

之后若运营者确认待归属返回是真实新增，可按收据明确归入成员或运营；若确认是聚合快照纠正，只追加关联纠正记录，不能声称某一次 NAI 消费已被撤销。已核销的损耗不能经此入口回冲。后续五分钟任务结案不会依赖人工先解释这笔聚合差额。

本地固定权益保留后，可能出现“本地固定余额为正、官方固定明确为 0”。此时仍允许已有 `allowPurchasedAnlas` 授权且个人购买余额足够的请求走纯购买池；不扣保留的本地固定权益。没有购买授权、购买余额不足、官方固定未知或快照过期时仍拒绝相应请求；其余固定优先规则不变。

## 资金来源与核销

`settings.fairQuota.operating` 仅保存运营可用、未归属待承担、待归属正差额、当前 V5 容量差额及待匹配收据。待匹配收据最多 100 笔，完成后移除；完整历史在现有持久 ledger，不增加 settings 历史数组。

运营可用只能来自：运营者主动划入本人已归属份额，或明确指定运营归属且已经观察到官方增额的唯一外部收据。登记收据表示来源已明确、等待官方余额体现，不能把注资意向当资金；登记本身不增加可用余额。内部划入同时减少本人可用、增加运营可用，保持总额；运营余额从不作为普通成员调用的保险资金门槛。

新的聚合缺口可以使用已有同资源运营余额承担，剩余保留待承担；之后的核销必须关联当前差额事件。历史收据、差额和累计核销查询覆盖 SQLite 冷历史，不能依赖最近 1000 条热 ledger。相同收据相同操作重试返回原处理；相同收据不同操作拒绝。购买池和固定池不互相补账。

聚合事件的 `observedAmount` 表示本次新观察到的下降；`amount` 表示该观察点可关联核销的累计差额，不能把历次 `amount` 相加当总损耗。V5 事件的 `amount` 是当时容量差额，`delta` 是变化；恢复事件属于估计来源核对，均不是单笔实际收费证明。

现有已鉴权管理接口新增以下操作，后续管理页会使用同一入口。仅 owner 或既有本机管理员可访问；本人划入的来源固定为部署配置 `OWNER_USER_ID`，客户端不能选择他人。

| action | 必要字段与含义 |
| --- | --- |
| `operating-contribute` | `receipt`、`resource`、`amount`；从运营者本人份额划入 |
| `operating-register-funding` | 同上；`destination` 为 `members` 或 `operating`，默认后者。默认登记未来新增；只有 `fromUnattributed: true` 才从已观察的待归属入账确认新增来源 |
| `operating-cover-loss` | 同上加 `lossEventId`；用已有同资源运营可用承担当前差额 |
| `operating-reconcile-return` | 同上加 `lossEventId`；运营者提供确认后纠正未确认聚合回跳，既不发新额度也不回冲已核销损耗 |

`receipt` 使用唯一业务标识，勿填写密钥；记录保存操作人、来源、资源和金额。V5 外部余额跳变与自然恢复不接受为外部新注资，只支持运营者本人份额划入。

## 持久化与验证边界

沿用现有 `store.update` 串行变更及同步 SQLite 提交，未增加通用存储写入规则。10 个生产同步入口显式纳入 ledger；派发同时提交与任务无直接关系的资源差额。管理预览、删除预览和启动器副本隔离 ledger，不能污染真实账本。

合成回归包含原资源退款、固定/购买下降、纯购买准入边界、V5 恢复不重复发放、内部划入守恒、先登记后入账、待归属两种反例、同池核销、冷历史重试、数据库写失败回滚，以及真实 HTTP 鉴权与同步落盘。测试不调用真实 NAI。
