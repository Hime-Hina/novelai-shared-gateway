# 失败退款与资源核对的当前实现

本文件对应 F03 的四片实现：尝试证据与原资源退款、聚合资源差额与明确来源运营资金、五分钟核对和迟到结果调整，以及管理查询、软告警与成员领取。真正的文件崩溃恢复属于 F10，不能据此宣称已经解决全部崩溃恢复。

## 三件事分开记录

- 成员本地预扣和退款：固定 Anlas、购买 Anlas、V5 分开；退款只退原预扣一次。`reserved` 到终态的持久状态迁移负责幂等，成功后的重复失败不退款。
- F05 后终态凭据保存在按 job ID 查询的 `fair_quota_settlements`，不再随每次额度摘要遍历。任务内的 `fairCharge` 保留展示用途，结算以冷热持久凭据为准。
- 上游消费证据：`generation_reserved` 在派发事务中保存尝试身份、操作、成员/账户、批次、本地原金额、候选资源和安全快照。实际失败后追加退款及疑似消费事件；报价不等于 NAI 实扣。本地 Anlas 续用的 V5/Anlas 是互斥候选，不能相加。
- 聚合来源差额：同步发现无法由已有结算抵消的 Anlas 下降时，保留成员权益，记录 `resource_gap_observed`，不按份额扣其他成员。记录只能说明聚合余额有缺口，不证明某一笔请求被收费。

V5 当前容量差额独立记录。整数官方快照保留一个百分点的精度边界，不把边界内的舍入误差认定为实扣。可信恢复速率产生的恢复先偿还原有续用估计负债，再抵消容量差额，剩余才分给尚未满额的成员。已有运营 V5 份额也计入总来源占用，不能因为转入运营钱包就再给成员恢复一份。恢复追加事件，不删除历史。

## 负差额、正向回跳与真正新增

普通没有未归属缺口的官方新增 Anlas 继续自动按既有份额分配，不要求每次充值/续订登记收据。明确登记为运营注资的新增先匹配收据，剩余才进入普通分配。

已有未确认的聚合负差额时，单次正差额可能是快照回跳，也可能是真实新充值。现有同步字段只有聚合余额，不能可靠区分，因此仅将可能对应缺口的部分记为 `unattributedReturns`，超出这部分的新增仍自动分配。待归属余额不是运营收入，不自动核销损耗，也不作为新的调用限制。

| 反例 | 处理 |
| --- | --- |
| 官方固定 10000 → 0 → 10000，缺少充值或快照纠正证据 | 成员仍保留原 10000 权益；保留 10000 未确认缺口及相应待归属返回，不把钱包变成 20000，也不宣称损耗已消失 |
| 有明确公共新增 1000 的唯一收据，同时还存在旧缺口 | 新 1000 照常按份额分给成员，旧待承担不变；不挪用成员新增自动填运营损耗 |

之后若运营者确认待归属返回是真实新增，可按收据明确归入成员或运营；若确认是聚合快照纠正，只追加关联纠正记录，不能声称某一次 NAI 消费已被撤销。已核销的损耗不能经此入口回冲。五分钟任务结案不会依赖人工先解释这笔聚合差额。

本地固定权益保留后，可能出现“本地固定余额为正、官方固定明确为 0”。此时仍允许已有 `allowPurchasedAnlas` 授权且个人购买余额足够的请求走纯购买池；不扣保留的本地固定权益。没有购买授权、购买余额不足、官方固定未知或快照过期时仍拒绝相应请求；其余固定优先规则不变。

## 资金来源与核销

`settings.fairQuota.operating` 仅保存运营可用、未归属待承担、待归属正差额、当前 V5 容量差额及待匹配收据。待匹配收据最多 100 笔，完成后移除；完整历史在现有持久 ledger，不增加 settings 历史数组。

运营可用只能来自：运营者主动划入本人已归属份额，或明确指定运营归属且已经观察到官方增额的唯一外部收据。登记收据表示来源已明确、等待官方余额体现，不能把注资意向当资金；登记本身不增加可用余额。内部划入同时减少本人可用、增加运营可用，保持总额；运营余额从不作为普通成员调用的保险资金门槛。

新的聚合缺口可以使用已有同资源运营余额承担，剩余保留待承担；之后的核销必须关联当前差额事件。历史收据、差额和累计核销查询覆盖 SQLite 冷历史，不能依赖最近 1000 条热 ledger。相同收据相同操作重试返回原处理；相同收据不同操作拒绝。购买池和固定池不互相补账。

聚合事件的 `observedAmount` 表示本次新观察到的下降；`amount` 表示该观察点可关联核销的累计差额，不能把历次 `amount` 相加当总损耗。V5 事件的 `amount` 是当时容量差额，`delta` 是变化；恢复事件属于估计来源核对，均不是单笔实际收费证明。

现有已鉴权管理接口和管理页使用以下操作。仅 owner 或既有本机管理员可访问；本人划入的来源固定为部署配置 `OWNER_USER_ID`，客户端不能选择他人。

| action | 必要字段与含义 |
| --- | --- |
| `operating-contribute` | `receipt`、`resource`、`amount`；从运营者本人份额划入 |
| `operating-register-funding` | 同上；`destination` 为 `members` 或 `operating`，默认后者。默认登记未来新增；只有 `fromUnattributed: true` 才从已观察的待归属入账确认新增来源 |
| `operating-cover-loss` | 同上加 `lossEventId`；用已有同资源运营可用承担当前差额 |
| `operating-reconcile-return` | 同上加 `lossEventId`；运营者提供确认后纠正未确认聚合回跳，既不发新额度也不回冲已核销损耗 |

`receipt` 使用唯一业务标识，勿填写密钥；记录保存操作人、来源、资源和金额。V5 外部余额跳变与自然恢复不接受为外部新注资，只支持运营者本人份额划入。

## 持久化与验证边界

沿用现有 `store.update` 串行变更及同步 SQLite 提交，未增加通用存储写入规则。10 个生产同步入口显式纳入 ledger；派发同时提交与任务无直接关系的资源差额。管理预览、删除预览和启动器副本隔离 ledger，不能污染真实账本。

合成回归包含原资源退款、固定/购买下降、纯购买准入边界、V5 恢复不重复发放、内部划入守恒、先登记后入账、待归属两种反例、同池核销、冷历史重试、数据库写失败回滚，以及真实 HTTP 鉴权与同步落盘。测试不调用真实 NAI。

## 五分钟核对与迟到结果

只有已经判定无法交付、完成本地退款且上游消费未知的尝试才创建 `job.generationReview`。其中 `firstUnknownAt` 及 `deadlineAt = firstUnknownAt + 300000` 在首次失败事务中持久化；重复失败和重启不重置。明确未发送的取消不创建核对，正常 `running` 任务也不会因为经过五分钟就被这个流程标成失败。

独立本地后台任务启动即检查，之后每十秒检查一次，每批至多 100 条。查询使用持久 jobs 的 JSON 表达式部分索引，覆盖冷历史，不依赖上游额度刷新、账户启用、网络通畅、派发冷却或是否存在后续调用。到期如有已登记且内容完整的本地产物，追加找回证据；否则结束核对并追加 `generation_loss_estimated`。它不会重新发送原请求。

结案明确记录可支持的候选估值或“金额未定”、原首次时间、原截止时间、实际结案时间，以及 `operator_pending_attribution` 运营待承担状态。候选仍为互斥关系，`actualConsumed` 保持 `null`，没有证据时不写确认零消费。

按尝试记录的运营风险估计与聚合缺口可能指向同一损耗。结案标记 `operator_attempt_estimate_nonadditive` 与 `aggregateSettlement: unmatched`，不加入 `operating.unfunded`，不再自动核销运营资金。管理查询与告警必须分开展示，不能直接相加为已确认实耗；结案只是结束核对等待，不消除运营责任。

完整图片在退款前到达时按原成功路径结算。退款后到达时，保留任务 `failed` 历史、原失败时间和原退款，保存 `imageId`，追加关联原损耗/结案的 `generation_result_recovered`；不突然补扣成员。图片只能证明产物完整，不能倒推出 NAI 实际收费。重复迟到回调先在现有串行提交中检查已有图片，因此只保存一次文件和调整记录，也不会重复减少账户在途计数。

任务响应新增 `lateResultAvailable`；既有 `imageId` / `imageUrl` 可用于领取迟到图片。成员摘要增加 `lateResultAvailable`、`imageId` 和 `imageUrl`，并通过独立的 `lateResults` 列表展示最近找回的本人结果。已经返回的失败响应不改写，现有 NAI/OpenAI 生图响应包形状不变。现有完整结果查询与图片访问权限继续生效。

`0002_generation_review.sql` 将旧疑似损耗记录的首次时间带入核对字段，不以升级时间延长窗口。确实缺少首次时间的旧记录保留空时间并立即进入金额/证据核对，不伪造时间。Drizzle Kit 0.31 对带逗号 JSON 表达式生成了错误引用，迁移 SQL 已按 schema 意图校准；回归通过实际 `EXPLAIN QUERY PLAN` 验证部分索引命中。该迁移向前执行，仍应先备份生产库。

F03 本片当时尚未覆盖“文件写成后、SQLite 提交前崩溃”的孤立文件找回；后续已由 [F10 产物恢复](result-recovery.md)补齐。这里的回归记录使用虚拟时间、冷缓存与重启、重复关闭、写失败重试、迟到证据，以及完整服务的离线停用自动结案和真实 HTTP 图片领取，未请求真实 NAI。

## 管理查询、软告警和成员领取

`GET /api/member/owner/member-management?view=losses` 与本机管理员别名 `/api/admin/member-management?view=losses` 独立读取损耗视图，沿用既有鉴权和来源限制。视图返回当前运营余额/缺口/待匹配收据、最近 24 小时及 30 天的风险和聚合差额、软告警，以及每页 50 条的历史事件。`before=nextCursor` 继续读取更早记录；历史不限于运行时的最近 1000 条 ledger。

尝试风险只统计 `generation_loss_suspected`，按尝试去重。后续估计结案、退款、找回事件不重复计成新损耗。V5、固定 Anlas、购买 Anlas 三个候选资源分别累计，互斥候选不能跨资源相加；金额未定单独计数。聚合 Anlas 只累计本次新下降 `observedAmount`，V5 只累计正 `delta`；它们与尝试风险分别展示，不相加为实际消费。

| 默认观察项 | 阈值 |
| --- | --- |
| V5 最近 24 小时 | 1 点 |
| 固定 Anlas 最近 24 小时 / 30 天 | 100 / 500 |
| 同成员最近 24 小时疑似尝试 | 3 次 |
| 购买 Anlas 最近 30 天 | 任一正数候选风险或聚合差额即提示 |

每个资源的候选风险与聚合新增差额分别比较同一阈值，任一达到即提示一次；不将两者相加后判断。阈值为 0 时，有正数风险就提示。成员频率提示显示当前安全用户名，成员已删除时保留稳定 ID 以便追溯。所有告警只用于观察，无论运营余额、阈值、未匹配差额如何，都不新增调用准入限制或停止退款。

同一管理入口 `POST action=loss-alert-policy` 接收 `expectedVersion` 与上述四个可调阈值，返回 `{policy}`。版本与成员分组配置无关；过期版本返回 409。数值必须有限且非负，Anlas/次数必须为安全整数。阈值设置和 `loss_alert_policy_updated` 审计在同一 SQLite 事务提交；审计保留旧/新阈值和版本、服务端鉴权得到的操作人，失败则一起回滚。

历史事件只返回白名单投影：事件身份/类型/时间、任务与成员身份和安全用户名、资源金额及候选关系、证据等级、关联事件/收据、操作人，以及策略变更前后值。不会返回提示词、成员 Key、Discord 令牌或原始上游错误。运营视图的 `gapEventIds.v5` 对应 V5 当前差额事件；待匹配注资只返回收据、来源资源、归属、剩余金额和登记/快照时间等必要字段。

成员 `me.jobs` 增加签名 `imageUrl` 和 `charge.fixed` / `charge.purchased`；历史没有分池字段时为 `null`，不伪造为零。`me.lateResults` 从 SQLite 本人完整历史按 `lateResultAt` 倒序取至多 10 条，字段为 `id/model/createdAt/lateResultAt/imageUrl/charge`。签发前同时验证有效成员、任务所属 Key 和图片所属 Key，缺失或不匹配的图片不签发。沿用现有 15 分钟签名链接，不在 URL 放 Key；成员 Cookie 的 `/api/member` 路径不会阻止领取 `/api/images/.../content`。领取保留原失败状态和分池退款，不发上游请求，也不再次扣款。

`0003_failure_accounting_queries.sql` 只添加三个索引：损耗类型/时间、按顺序分页的损耗历史部分索引、成员迟到结果 JSON 表达式部分索引。数据库当前共有 4 条迁移。Drizzle Kit 对 JSON 表达式的转义已按 schema 意图校准；分页显式使用有序部分索引，避免规划器转而按类型扫描后将整段历史排序。滚动汇总在 SQLite 内计算，只将有限标量和当前页事件载入 JS。部署前仍须备份，迁移只能向前；不对生产执行 schema push。

第四片回归覆盖 1116 条冷账本分页、窗口端点/未来时间、候选去重与金额未定、聚合独立告警及禁止相加、零阈值、重启、真实索引计划、鉴权/来源限制、独立策略版本与审计回滚，以及超过 3000 条任务后的本人冷历史和无 Cookie 的真实 HTTP 签名图片领取。无真实 NAI 请求。

冷表。settled/refunded 从 settings.fairQuota.reservations 移出；reserved 和未识别项
原样保留，不因找不到任务就推断退款。删除任务日志不会删除这份结算凭据。
没有新增热 Map、通用归档层或重复索引。

归档与设置、任务、账本在原同步 SQLite 事务内提交，成功后才替换热设置。
