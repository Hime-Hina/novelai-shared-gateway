# 近期任务排队基线

这是 P01 的生产历史只读基线，统计截止为 **2026-10-17 02:30 Asia/Taipei（2026-10-16 18:30 UTC）**。它衡量当前已持久化任务的等待与执行，不代表 HTTP 总请求量，也不是新版本压测结果。

最近 24 小时 514 个任务全部成功，本地排队 P50 为 **0.009 秒**，P95 为 **15.215 秒**，最大 **147.092 秒**。大部分积压时的派发间隔紧贴既定十秒规则；存在一个不能由这条规则解释的孤立长尾。当前证据支持先补清晰的等待原因和队列上限，不能据此认定需要增加上游并发或缩短十秒间隔。

## 来源、口径与安全边界

- 从实际运行的 systemd 服务核实工作目录及进程已打开的 SQLite 文件；以 `mode=ro`、`PRAGMA query_only=ON` 和同一只读事务提取。没有导入应用入口、启动第二个调度器、写生产数据库、重启服务或发起 NAI 请求。前后核对服务仍在运行，进程未改变。
- 统计实现为 [queue-baseline.py](../scripts/queue-baseline.py)，只用 Python 标准库；SQL 位于 `ROWS_SQL`。复用了现有 `readOwnerJobRows` 的持久历史口径，增加阶段时间、入口、状态与分位数；没有调用会刷新额度的 HTTP 查询接口。
- 生产库仅有 608 个任务，首条提交为 **10 月 15 日 23:10:05**，末条为 **10 月 17 日 01:01:20**（台北）。七天查询窗口为 10 月 10 日 02:30 至 10 月 17 日 02:30，但实际记录跨度只有约 25 小时 51 分；不能将较早日期记为完整观测到的零流量，也不能推断缺失原因。
- 每条 `jobs` 记录计一个任务。当前批量请求逐张创建任务，尚未创建的剩余张数不在历史中；本报告不将任务数称为 HTTP 调用数或完整到达需求。
- 按 `created_at` 归属窗口，右边界不包含；24 小时窗口是滚动窗口，和 owner 页面按台北日界取样的范围不同。时间段按台北小时分组。分位数采用 nearest-rank，即排序后第 `ceil(n×p)` 个值。
- 缺失、无法解析和负数阶段耗时记为未知，不填零。取消/超时通过结构化状态和固定错误类别识别，不输出原始错误、提示词、图片、IP、成员名称或凭据。成员仅为本次查询内的 M01–M05，无可公开映射，也不能跨报告跟踪同一成员。
- 不保存生产原始行或数据库副本。只读统计得到的匿名 JSON 留在 Git 忽略的私有目录，公开材料只有本报告与合成自检。任务时间戳、ID、成员标识与原始日志不逐条公开。

## 十秒间隔之外的等待

按同一持久账户标识的 `startedAt` 排序，用前一任务的完成时间计算：

```text
最早可派发 = max(本任务提交时间, 前一任务完成时间 + 10 秒)
额外空隙 = max(0, 本任务派发时间 - 最早可派发)
```

仅使用前序完成已知、同账户、无记录重试且时间不重叠的相邻记录。该算法只扣除已知十秒规则，**没有扣除无法回放的容量退避、账户资格或暂停状态**；所以“额外空隙”是排查线索，不等于无故浪费的时间。未知前序不记零；七天窗口 608 个已派发任务中 606 个可计算、2 个未知（0.33%），24 小时 514 个均能在现存历史中找到可用前序。

## 对实施顺序的影响

1. **F04 保留准入上限与原子停止接单**。本样本未出现超大积压，不能用它证明当前无上限是安全的；实施初值应结合三条已观测峰值与合成突发到达测试，并同时比较拒绝率、等待分位数和成员公平性。
2. **F06/F10 补完整请求、批次与恢复状态**。历史仅反映已经创建的单图任务，无法检查未创建子任务丢失、第三方重试和崩溃中的消费证据。
3. **F12 补最少调度观测信息**：任务可派发时间、最近阻塞原因及其开始/结束时间，原因使用固定枚举（账户在途、成功间隔、故障退避、额度检查、停止接单）；把持久化提交完成与 HTTP 完成时间分开。通过隔离环境模拟 147 秒停顿，检查等待提示与恢复；不补写猜测的历史原因，不扩展成新的遥测框架。
4. **保留单并发和十秒规则**。通常积压派发仅比十秒多几毫秒；现有证据不足以支持策略调整。查清孤立长尾优先于缩短所有任务间隔。
5. **D01 重新采样比较**。使用相同统计截止、时区、窗口和分位数口径；隔离环境以相同到达序列和模拟耗时比较新旧版本，成功/失败/取消/拒绝和未知字段都保留。当前三次失败不足以验收故障阶梯，需要合成失败与中断测试。
