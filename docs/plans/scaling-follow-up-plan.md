# 多执行器、多账号与数据库迁移后续计划

更新日期：2026-11-01，Asia/Taipei。

状态：**后续设计保留，未启动、未承诺排期。** 用户已明确将多执行器、多账号调度和数据库系统迁移留到后续；多车队/多来源关联设计一并保留在此。本文不是[当前重构计划](architecture-refactor-plan.md)的实施前置或发布验收项。

## 1. 与当前计划的衔接

当前计划只实现唯一执行器、单一绑定 Opus、SQLite 内部事件溯源，以及[成员生成接口契约](../contracts/member-generation-contract.md)。本文件保存前一版已讨论的扩展设计，避免将来重读聊天史，但不要求当前新增 fleet 表、多账号选路、租约/跨进程状态或 PostgreSQL 驱动。

后续启动时，以当时已交付事件和成员 API 版本为基线：将共享配置聚合明确映射到默认 fleet，保留原 member/account/request/attempt ID、原 Key 默认来源、幂等映射和费用授权。已有事件不原地改写；新 scope 通过增量 schema、导入事实及兼容读取加入。新成员 API 不接受的 fleet/account 选择须通过明确版本扩展开放，不能默默改变旧请求来源。

“业务代码少改”“迁移时不丢账”和“完全不停机”是不同验收目标。本文提供设计和可执行验证方向，不承诺换连接字符串即可迁移，或无需演练就零停机。

## 2. 后续业务语言与来源模型

### 2.1 固定业务含义

| 名称               | 含义与权威身份                                                            | 不承担的含义                                        |
| ------------------ | ------------------------------------------------------------------------- | --------------------------------------------------- |
| Member             | 站点内稳定身份，`memberId`                                                | API Key、Discord token、用户名都不是业务主键        |
| Fleet              | 一套成员资格、分配与管理边界，`fleetId`                                   | 当前四个顶层 group 不自动改称四个车队               |
| Membership         | 成员在一个车队内的资格，`membershipId`，唯一 `(fleetId, memberId)`        | 同一成员在另一车队的资格和钱包                      |
| Group              | 车队内部的份额组织，`(fleetId, groupId)`                                  | 独立可消费钱包或物理上游账号                        |
| UpstreamAccount    | 一个真实 NAI 账号，`accountId`，凭据轮换不换身份                          | PST 字符串；同一个账号的两份 PST 不能当两个容量来源 |
| Funding allocation | 上游资源向车队的分配，`(accountId, fleetId)`                              | 把同一个官方总余额分别完整分给多个车队              |
| Wallet             | 某成员资格在某来源账号下的本地权益，`(membershipId, accountId, resource)` | 官方实时余额、可在不同账号间自由兑换的总资产        |
| Request            | 一次已受理的规范化意图，`requestId`                                       | HTTP 连接、单张图片或一次重试                       |
| Job                | 一张图或一个辅助操作，`jobId`，属于一个 request                           | 重新提交同一 HTTP 请求                              |
| Attempt            | 一个 job 的物理上游尝试，`attemptId`                                      | 网络重试次数；当前契约仍为每 job 最多一次生成尝试   |
| Artifact           | 已验证的产物描述，`artifactId`                                            | 预览帧、未验证文件或一个永久公网 URL                |

新记录使用这些稳定 ID；`userToken` 等旧归属字段只留在兼容读取和迁移中。成员删除保留必要的历史 ID/tombstone，凭据撤销独立处理。查询返回的昵称和 Key 不参与历史关联。

### 2.2 多车队、多来源的后续模型

- 现有业务导入一个明确的默认 fleet，现有四组和成员规则保持不变。只有边界适配器可以补默认 fleet，领域函数必须接收明确 scope。
- 一名成员可有多个 membership；一个 fleet 可有多个账号资源来源。API Key 绑定明确的 membership/fleet；既有无 fleet 参数的客户端由原 Key 解析到默认归属。
- 若一个真实上游账号服务多个 fleet，官方快照、恢复总预算、Anlas 来源和物理并发都只在该 account 层计算一次，然后按明确的账号→车队分配继续分到组与成员。当前默认 fleet 获得该账号 100% 的既有分配。
- 同源份额总和不得超过 100%；有余额、在途预留或未知执行证据时，变更来源绑定必须通过显式命令处理，不能修改一个外键完成“搬钱包”。V5 百分点和 Anlas 均不跨账号自动兑换、合并或故障转移。
- 账号登记尽可能使用上游验证后的稳定账号标识。如果现有协议不给出可验证标识，则登记明确的受管理账号身份，轮换 PST 必须关联原身份；不能用 PST 哈希证明两个凭据属于不同物理账号。增加真实第二账号前要完成身份核对。
- owner 的站点管理身份与 fleet 管理权限分开表达；从认证结果解析 scope，不信任客户端自由填写的 `fleetId/memberId/accountId`。所有查询、缓存、结果领取和 SSE 过滤都遵守同一归属。

旧 Key 导入时固定现有默认来源账号；不会因新增账号就改变旧客户端的扣款来源。新凭据或显式调整后的来源配置才能允许多来源选路。旧 `/user/subscription` 等单余额响应继续表示该默认来源，不把多个账号的 V5 百分点相加；新多来源查询返回按 account 分列的额度和默认来源。全账号官方余额由账号管理权限查看，fleet 页面仅显示其权益及获准公开的容量信号，不能泄漏其他 fleet 的成员和钱包。

### 2.3 数据键与分区

| 对象                         | 唯一性/归属约束                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------- |
| 生成幂等键                   | `(fleetId, memberId, operation, keyHash)`；相同键、不同指纹返回冲突；跨 fleet 互不复用 |
| 请求、job、attempt、artifact | 全局稳定 ID + 明确 fleet/member/account 归属；ID 难猜不能替代授权                      |
| 余额与运营来源               | 按 `accountId` 隔离，成员维度使用 membershipId；不依赖全局 `settings.fairQuota`        |
| 配置版本                     | fleet 分配版本、account 分配版本、策略版本分别存在；一次跨边界变更校验全部受影响版本   |
| 任务选择                     | account 下的持久队列顺序；待激活 child 不提前领取队头位置                              |
| 查询与缓存                   | 至少包含授权 scope、相关版本和查询条件；不能跨 fleet 命中成员缓存                      |

## 3. 后续执行与调度设计

### 3.1 明确当前承诺与实现接口

后续实施时先在一个本地 SQLite 库上验证两个命令/执行进程，消除依赖进程内全局对象的业务正确性。SQLite 仍一次只提交一个写事务；多进程受理正确不代表写吞吐线性增长。生产可以继续只启一个执行器。

命令层只需要明确的 `commitCommand`、`readProjection`、`claimAccountDispatch` 等数据操作，先只有实际可用的 SQLite 实现。未来跨主机改为 PostgreSQL 共享事务库，替换这几个持久化操作；领域决定、事件、归属、幂等和协议接口保持。不会把 SQLite WAL 文件挂到网络盘上作为跨主机共享数据库。[SQLite WAL 与事务边界](https://www.sqlite.org/wal.html)、[SQLite 写事务](https://www.sqlite.org/lang_transaction.html)

PostgreSQL 适配遵守[当前计划](architecture-refactor-plan.md)第 7 节的事务与版本契约，对 stream/账号行按稳定顺序使用行锁，并重试可安全重试的事务冲突；不重试已授权的外部生成。普通数据库 sequence 仍不能代替有提交顺序保证的游标。[PostgreSQL 行锁](https://www.postgresql.org/docs/current/explicit-locking.html)

本后续计划交付实际 PostgreSQL 适配、共同契约测试和数据迁移演练，再验证第二主机接入；不会只定义接口就称切库完成。领域边界应减少业务改动，但 schema、查询、锁、认证、载荷和产物存储的适配工作仍须实施。

### 3.2 账号派发权与 fencing

持久 `account_dispatch` 行至少包含 accountId、executorId、fencingToken、leaseUntil、attemptId、阶段、确定冷却截止和最后观测。accountId 唯一；fencingToken 每次拥有权变化单调递增，所有状态提交带预期 token。心跳只续约，不追加一条没有业务价值的领域事件；获得/释放/隔离拥有权有可追溯记录。

fencingToken 由数据库实例 epoch 与单调计数组成。恢复旧备份时创建新 epoch，并在重新开放派发前确认旧进程的发送能力已终止；只提高数据库 token 仍不能隔离旧进程对 NAI 的网络访问。测试副本沿用已有脱敏和模拟上游流程，不能带着原身份成为另一份生产派发者。

派发步骤：

1. 从持久队列选出适合该来源账号的 job，检查 fleet/membership、来源钱包、免费限制、截止和接单代次。
2. 同一事务内领取账号占用、生成唯一 attempt、预留额度，并记录派发授权。绑定账号后，该 attempt 不再切换到另一个账号。
3. 持有者在事务外发起 provider 请求，所有结果记录带 attemptId 和 fencingToken。进程内 `runningJobControls` 只管理本进程连接，不能决定其他进程可用余额或槽位。
4. 结果先经过描述提交、字节持久化/验证，再把发布、结算、冷却和下一 child 激活原子提交。失败按原资源退款，留下未知或明确失败证据。
5. 完整结束本地物理连接后才释放物理占用，遵守 account 级持久冷却。逻辑 job 超时、退款或五分钟估计结案不能自动证明旧持有者已失去发送能力。

**租约过期不能单独授权另一个进程接管已获得发送授权的账号。** fencing 可以拒绝旧进程写数据库，但 NAI 不会替我们验证这个 token；旧进程若在检查与 fetch 之间暂停，恢复后仍可能发出请求。

因此区分以下情况：

| 状态                                        | 接管规则                                                                                      |
| ------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 从未提交派发授权的 claim                    | 租约过期可 CAS 回收；旧进程后续授权必因 token/版本不符被拒                                    |
| 已授权、仍可能发送或等待响应                | 置 account 为隔离/排空；不把同 attempt 交给新执行器重发                                       |
| 确认旧进程已退出，或已经隔离其发送能力      | 通过恢复命令检查产物、结算和持久冷却；原 attempt 按结果/未知规则处理，再释放后续新 job        |
| 跨主机网络分区，旧主机是否仍能访问 NAI 未知 | 保留该 account 隔离；需进程/主机/出口隔离证据完成接管，其余账号可继续工作                     |
| 旧持有者提交迟到完整产物                    | 不能用旧 token 修改余额；通过当前恢复命令验证原 attempt、归属和摘要后接收证据，保留已退款事实 |

启动和正常关闭都复用这套拥有权规则：停止新授权、处理本进程在途、持久化结果再退出。不要依靠租约 TTL 推断物理外部请求已经结束，也不承诺仅凭事件溯源就能做到无停顿的跨主机生成接管。

### 3.3 多来源选择、批次公平与配置

请求受理时保存允许使用的来源范围和原参数意图；实际派发按当前有效资格、该成员来源余额、账号可用时间和持久队列顺序选择账号。同等条件按稳定 accountId 排序，避免两个进程各自随机选路。来源选择和预留一起提交；不能先选账号、在事务外检查余额、最后再扣款。

单个账号继续串行及完成后冷却；多个不同账号可以独立执行。共用一个账号的不同 fleet 共用物理队列和冷却，按持久顺序服务，不各拿一个“全额并发槽”。批次每个 child 单独结算，上一 child 完成后下一 child 才排到适用来源的队尾，保持现有 A1→B1→A2 行为。

现有每成员上限按 membership 解释，当前全局未完成任务上限继续作为整个部署的资源上限；引入 fleet/account 不自动把全局上限乘以实例数。车队可有自己的业务限额，但最终准入同时满足部署资源预算；命令在同一事务按相应范围计数，普通成员只能查询获准范围内的队列详情。

生成失败不自动把原 attempt 转发到另一账号。若未来提供用户明确发起的重新生成，它是新 request，关联原 request 但再次经过报价、授权和幂等；不能把“多账号路由”偷偷变成重复消费重试。

新接口可以明确选择 membership/fleet；旧接口由凭据决定默认范围。配置和管理视图使用同一套来源和资格命令，增加账号时需要登记、分配并验证凭据，不增加第二份 wallet 实现。

### 3.4 不能遗漏的进程本地状态

| 现有状态                          | 多进程处理                                                                                               | 后续验收                                                   |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 热钱包、幂等 cache、queueDraining | 数据库版本/事务决定；本地只缓存、合并唤醒                                                                | 两进程交替修改、陈旧 cache 拒绝写入                        |
| `accountQuotaRefreshPromise`      | 按 account 的持久刷新 claim 与观测序号去重，旧观测不覆盖新观测                                           | 两进程同刷新只采纳有效最新事实，不重复恢复                 |
| 正在读取的正文预算                | 临时 payload claim 持久标记 owner、token、字节和期限；按有界块预留，受理事务移交给活动请求统计，断线释放 | 并发上传＋受理不突破既有总预算、不双计；过期持有者提交被拒 |
| Discord OAuth `states`            | 摘要、Cookie 绑定和期限进入认证存储，回调原子单次消费                                                    | 起始/回调落到不同进程仍成功，重复回调拒绝                  |
| Discord `checks`/refresh 去重     | 按身份/凭据版本的持久 claim；刷新不明不能并发再刷；成功凭据条件提交                                      | 轮换后旧响应不覆盖新 grant，暂时故障仍为真实错误           |
| 登录限流 `attempts`               | 可信 IP/用户名维度使用共同认证存储原子计数；短期认证数据不写长期领域事件                                 | 两进程交替请求不能翻倍限额                                 |
| waiter、预览和状态 SSE            | waiter 以持久终态补读；连接本地保留，预览路由到 attempt 持有者，断线校准                                 | 连到非执行进程仍能查询/领取最终结果；预览丢帧不影响结算    |
| 连接上限                          | 保留每进程硬预算；成员/全局配额由有期限的连接 claim 统一计数                                             | 多入口不能绕过成员上限；异常退出可回收                     |

这些机制限定为当前共享状态的所有权，不合并成一个覆盖所有用途的泛型租约框架。安全撤销、免费限额和钱包准入必须强一致；可以跳帧的预览与可补读通知不需要和扣款同等持久性。

### 3.5 产物位置与跨主机

当前沿用本地发布与 R2 冷归档，`ImageStorage` 继续屏蔽实际读取位置。产物描述增加明确 storage namespace/backend/locator，不能把一个节点的绝对路径当作全群可读地址。

多主机运行时，结算成功前必须将最终产物发布到所有获准领取方可访问且经过校验的存储；可把已有 R2 能力用于主产物存储。临时文件属于具体 attempt/节点。只有节点本地暂存、还没有可恢复的持久回执时，不能宣称成功。远端 PUT 超时按相同 key/摘要核对，不能重发生成；归档也不能在校验回执提交前删除唯一副本。

## 4. 数据库系统迁移的实际交付

切库包括事件/关键投影与查询 SQL、schema/索引、事务和冲突处理、连接池、认证表、幂等回执、请求载荷及产物目录。事件重放能重建投影，但不代替秘密、会话和图片字节的迁移。当前 SQLite 内部的 opening baseline 导入与这里跨数据库系统的迁移分开验收。

- 实现 PostgreSQL 持久化操作，保持纯业务决定和成员/Native/OpenAI 契约；同一套金额、原子性、幂等、恢复和并发合同测试同时运行于两个数据库。
- 编写明确源/目标的导出、导入、事件重放和逐来源核对工具，覆盖金额精度、时间、唯一约束、被清理任务的幂等凭据、认证资料和载荷/产物引用。
- 预先复制/重建目标库，最终短暂停写并追平余量，验证一致后切换唯一写入方。重新开放前隔离旧执行器的发送能力并使用新的实例 epoch。
- 旧库恢复为只读证据，不能在目标已产生新消费后直接用旧备份覆盖。回退须携带新提交，或使用已验证的兼容程序。
- 若要求严格零停机，再单列增量复制、一致切点、认证/载荷尾部同步和读写路由切换；不能仅靠领域事件流遗漏非事件数据。

[当前计划](architecture-refactor-plan.md)使用全局 `event_clock` 保证完整提交游标，这会保留短暂串行提交点。高并发验收要测其锁等待与吞吐；必要时再设计能证明提交完整性的分区游标/消费位置，不能仅换普通 sequence 就跳过未提交事务。不得提前声称 PostgreSQL 会使应用吞吐线性增长。

当前 Nuxt＋唯一执行器的双服务测试不等于两个执行器共同写账本的测试。后续测试使用合成身份和模拟上游，生产仍须针对明确候选完成既有发布流程。

## 6. 设计依据与维护

数据库行为依据 [SQLite WAL](https://www.sqlite.org/wal.html)、[SQLite transactions](https://www.sqlite.org/lang_transaction.html) 与 [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)。账号来源和外部派发保证来自本项目的证据与约束，不声称 NAI 提供远程幂等或 fencing。
