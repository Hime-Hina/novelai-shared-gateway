## 2026-10-20 实施更新

以下原始草案保留作为背景；当前代码以本节和 [失败退款与资源核对](failure-accounting.md) 为准。维护者确认后，已先完成并校验数据库及相关文件备份，再于 2026-10-20 23:57（UTC+8）正式部署 `3ff71f5`。免费图策略仍保持关闭，详见 [发布与验收记录](production-release.md#2026-10-20-防滥用修复部署与验收)。

- 调度入口已经迁至 `server/gateway-runtime.ts`，配额、存储和成员接口使用 `.ts`；当前页面为 `web/app/components/ManagementMembers.vue`、`ManagementFreeImages.vue`、`ManagementLosses.vue`、`MemberQuota.vue`。
- 当前共享并发为 1，任务完成后至少冷却 10 秒；已有每成员 4 个、全局 16 个未完成任务上限和事务内准入检查，无需重复实现。
- 普通 Anlas 扣款保留至官方下降能够匹配，不再把扣款延迟误认为充值。充值与消费同窗只先分配可见净增额；经核实后可通过现有运营接口的 `operating-confirm-debits` 操作补齐差额，继续匹配已登记资金的归属，收据幂等且记录审计。
- 未知负差额先待核对，取消单次下降自动核销运营资金的行为。人工核销和快照纠正复用已有接口；同一待归属返回反复出现／消失不会重复计提缺口。未增加自动归车头扣款策略。
- `server/free-image-policy.ts` 实现滚动 24 小时免费图片检查。成功凭据持久化到 `free_image_usage`，按 job ID 去重；SQLite 触发器与普通结算、迟到完整产物同事务提交。迁移 `0011_free_image_usage` 从已有成功结算和仍存在的迟到任务回填，不伪造缺失历史。
- 免费图片策略默认关闭，当前只提供全体成员适用的默认值。管理页可配置提醒阈值和硬上限，`null` 表示不设置；站内告警在用量跨越阈值时记录，持续高用量不逐张新增告警。用量下降后重新跨越可以再次触发。
- 入队快速检查和派发前事务内复查覆盖网页、direct/OpenAI 和 Native 入口；多图逐张计数，缓存、幂等重放、预览帧不计，退款后完整迟到图片计一次。只有在成功记录能确定恢复时间时才返回 `Retry-After`，在途占满时提示等待结算。
- 成员页提供本人成功数、在途预留、上限和恢复时间，并显示共享差额及检查时间；不公开其他成员的钱包、密钥或生成内容。

策略读取沿用管理员／owner 的 `GET member-management`，返回 `freeImagePolicy` 和各成员的 `quota.freeImages`。保存使用同一已鉴权接口：

```json
{
  "action": "free-image-policy",
  "expectedVersion": 1,
  "policy": {
    "enabled": true,
    "warningThreshold": 800,
    "hardLimit": 1000
  }
}
```

上述数量仅是配置示例，不是官方安全上限。策略版本与分组版本独立；版本过期返回 409，参数无效返回 400，免费图片达到硬上限时 JSON 接口返回 429（旧 `/generate` 保留错误图片响应）。关闭策略不清空统计，提醒阈值和硬上限互相独立。

成员覆盖、自然日窗口、外部主动通知和自动归车头仍属于后续可选方案。正式升级前备份数据库；本次不自动追溯修改历史钱包或已核销记录。

## 一、问题与目标

1. 车头绕过网关使用官方源 API 时，消费无法可靠归属到车头的成员钱包。希望增加差额提示、人工归账，以及可选的“无法解释的消费统一归车头”策略。
2. 成员持续大量生成 V4.5 及更早模型免费图片时，目前只有共享账户并发保护，没有按成员的免费图片数量上限或阈值告警。希望支持管理员配置上限或仅提醒。

网关无法识别未经过网关的请求是谁发出的。自动归车头是一种管理员约定，不应在 UI 中表述成已确认的调用者身份。免费图片限制也只能覆盖经过网关的请求。

## 三、网关外消费：提示与归账

### 3.1 配置示例

```js
externalUsagePolicy: {
  mode: 'off', // off | notify | manual | charge-owner
  ownerUserId: null,
  confirmationSnapshots: 2
}
```

默认关闭保持兼容。启用前验证车头是账本中的有效成员；更换／删除车头时处理尚未结清的事件和欠额。配置修改记录管理员审计历史。

### 3.2 对账流程

1. 仅使用有效、新鲜的官方快照。
2. 有未结清的网关任务时暂缓自动归账，等待任务结算和更新后的官方余额。
3. 对账时考虑已知网关消费、额度恢复、官方余额精度和已有 fallback 抵消记录。
4. 在连续有效快照中确认差额后，创建持久化待处理事件。快照数量只是确认条件之一，不能保证能够排除所有扣款延迟。
5. 根据策略仅提示、等待人工确认，或扣车头对应钱包。
6. 车头余额不足时记录未清偿差额并告警，不继续转扣其他成员；实际派发继续受官方公共余额检查约束。

**不能每次把 `recordV5Reconciliation()` 的 `difference` 直接扣到车头。**该值表示累计差额，同一缺口会重复出现在刷新结果中。需维护已处理金额或独立对账基准，保证只处理新增差额；不能把暂时恢复正常后再次出现的同一延迟扣款当作全新消费。

### 3.3 分资源处理

- V5：官方可能只显示整数百分比，个人钱包又是估算值。保留精度容差，明确归账金额是估计值；优先支持提示和人工确认。
- Anlas：当前 `syncFairQuota()` 中无法解释的负差额会经 `distribute()` 按成员现有余额比例缩减。开启新策略时应替换这条分摊路径，改为待处理事件或车头归账。
- 订阅 Anlas 与购买 Anlas 分别对账；保留现有 fallback 抵消处理，防止同一消费重复记账。
- 官方余额突然增加、续订、账户失效、快照过期或更换源账户，不应直接视为外部消费或随意补发个人余额。

### 3.4 事件结构示例

```js
{
  id,
  accountId,
  resource, // v5 | anlasFixed | anlasPurchased
  amount,
  estimated,
  detectedAt,
  sourceCheckedAt,
  status, // pending | notified | charged | dismissed
  ownerUserId,
  chargedAmount,
  outstandingAmount
}
```

事件处理状态、钱包变化与对账基准更新必须在同一存储事务内提交，支持幂等处理和重启恢复。人工驳回应保存理由和处理依据，避免同一事件在下一次刷新中再次出现。

成员端提示可使用：“检测到网关外消费或未解释的共享余额差额，实际可用额度可能受影响。”成员端只公开共享风险摘要，不公开其他成员钱包、源 Key 或生成内容。

## 四、成员免费图片上限与告警

建议新增 `server/free-image-policy.js`，集中处理策略、窗口统计、名额预留和阈值事件。

### 4.1 配置示例

```js
freeImagePolicy: {
  enabled: false,
  window: 'rolling-24h',
  warningThreshold: 800,
  hardLimit: 1000 // null 表示只提醒
}
```

支持全局默认值与成员覆盖。第一版可只实现滚动 24 小时；如增加自然日模式，明确以北京时间划分日期。阈值为示例，不是推荐的官方安全上限。

### 4.2 免费图片判定

采用已有计价结果：

```js
quote.resource === 'free'
```

不只按模型名判断：V4.5 高分辨率、超步数或附加参考可能收费；V5 使用独立的恢复额度，不属于此计数类别。如果未来希望限制全部旧模型图片，可以增加独立的统计模式。

### 4.3 检查与结算

- 入队前快速检查，已达到上限时尽早拒绝，避免无效任务堆积。
- 派发前在 `reserveQueuedJob()`／`reserveFairQuota()` 所在存储事务内再次检查，并为该图片预留一个名额。前置检查不代替事务内检查。
- 成功生成后，把预留转为成功计数；失败、取消、超时清理时释放预留。
- 每个 job ID 只能预留和结算一次，所有终止路径复用同一幂等逻辑。
- 多图请求按现有单图拆分逐张计数；部分成功只累计成功图片。
- 缓存返回不计为新增生图；流式预览帧不计数，只在最终图片结算时累计。

核心判断示意，非可直接应用的补丁：

```js
if (
  hardLimit !== null &&
  successfulCountInWindow + activeReservations >= hardLimit
) {
  // 拒绝本张图片；返回明确错误和合理的 Retry-After。
}
```

滚动窗口按成功时间统计；在途预留在结算前始终占用名额。窗口事件与预留需持久化，不能在进程重启后清零。若采用 SQLite 查询，增加成员、计数类别、状态、成功时间的必要索引，避免每次扫描全部历史任务。

### 4.4 告警与显示

- 初次跨越提醒阈值时创建站内告警；持续高用量时去重，不逐张重复发送。
- 定义告警重新触发条件，例如用量先降到阈值以下再重新跨越，或采用可配置冷却时间。
- 管理员页面显示成员、窗口内成功数量、在途名额、阈值和触发时间。
- 成员页面显示已用数量、上限和下一次可用时间。滚动窗口达到上限时，一般以最早一张计数图片退出窗口的时间计算；若名额被在途任务占满，需提示等待结算，避免承诺不确定的恢复时间。
- 初期只做站内告警；邮件、Telegram 等主动通知可作为独立扩展。

### 4.5 建议额外增加排队上限

免费图片每日上限只限制成功用量，不能防止成员一次提交大量排队任务。建议另设每成员最大排队／未完成任务数，在任务创建事务内检查，覆盖全部生成入口。批量请求按拆分后的实际任务处理，保持现有单批最多一个排队任务的行为。

## 五、持久化与兼容

- 新策略默认关闭，已有用户升级后行为不变。
- 新状态纳入现有存储事务及 dirty rows／collections 持久化规则；不能只修改内存对象。
- 明确重启时如何恢复未结算预留，复用现有过期任务清理规则。
- 仅管理员可修改策略、指定车头和确认差额。成员查询只返回本人统计与共享风险摘要。
- JSON、multipart、ZIP、流式以及聊天生图入口最终执行同一策略，不由前端独立执行限制。
- 更新 README、配置说明和 API 错误说明。

## 六、建议测试

### 外部消费

1. 同一差额多次刷新／重启后只处理一次。
2. V5 整数舍入、恢复、估算误差与延迟扣款不误扣。
3. 网关任务未结清时不提前归账。
4. 两类 Anlas 与 fallback 抵消保持正确，启用新策略后不缩减其他成员钱包。
5. 车头余额不足时保存未清偿差额，不转嫁其他成员。
6. 人工确认、驳回和自动处理均幂等；车头变更有校验与审计。
7. 快照失效、续订或源账户变化时不产生未经核对的归账。

### 免费图片限制

1. 多个并发请求争抢最后一个名额，仅一个成功预留。
2. 多图部分成功、失败、取消、超时后计数与预留正确。
3. 缓存和流式预览帧不增加计数。
4. 重启不清空统计、不泄漏预留；迟到成功不重复结算。
5. 滚动窗口到期释放用量，边界时间正确。
6. 仅提醒模式不阻止生成；关闭策略保持兼容。
7. 告警去重，按定义条件重新触发。
8. 收费 V4.5 与 V5 不误算成免费图片。
9. 各生成入口都无法绕过策略；排队上限也不能被并发提交突破。

## 七、建议实施顺序

第一阶段：共享差额提示、人工归账、免费图片统计、阈值告警与可选硬上限。

第二阶段：在对账记录证明可靠后增加可选自动归车头策略，再扩展主动通知渠道。

以上方案无需重写整体架构。免费图限制的接入较直接；外部消费自动归账的主要复杂度在来源精度、延迟扣款、防重复处理和余额不足后的欠额管理。
