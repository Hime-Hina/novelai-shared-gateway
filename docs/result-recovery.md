# 结果持久性与崩溃恢复（F10）

适用范围是通过统一共享队列受理的网页、Native、direct、OpenAI、生图、
放大和 Vibe 编码。一个任务只有一次上游尝试；恢复不再次请求 NAI。已停用
的官方 Key 独立缓存路径及旧 inline 图片搬移不据此宣称同样的尝试恢复保证。

## 提交与恢复顺序

1. 检查任务、成员、账户、尝试和原结算凭据，在独立 SQLite 事务中提交
   `job.resultPending`：attemptId、imageId、file、operation、mimeType、byteLength、sha256。
   同时保留上游时间与状态证据，描述提交失败时不开始写文件。
2. 在现有串行写流程内，校验内容与描述一致，以 `wx`、0600 创建同目录
   `${file}.part`，完整写入、文件 fsync、rename 为最终文件、目录 fsync。
   已有同内容完整文件可复用；路径、长度、SHA-256 或格式不符则保留原文件
   和描述并报错，不覆盖、删除或猜测它属于哪个任务。
3. 同一账本事务写入图片元数据、任务终态、扣费结算或迟到结果、冷却与批次
   下一张激活，并删除 resultPending。失败回滚保留此前已提交的描述和文件。
   重试沿用原 imageId，重复完成不创建第二份结果，也不重复扣退。

图片继续使用 F07 的 PNG/JPEG/WebP 校验、64 MiB、16384 边长及原像素限制。
Vibe 编码作为非空 opaque 二进制处理，以原媒体类型、长度和 SHA-256 验证，
不把它送进图片解码器。新结果记录保留 operation、byteLength、sha256。

启动先创建图片目录，再从部分索引按 ID 分页查询待恢复任务，逐条验证；
完整 `.part` 可补发布，完整最终文件可直接复用。随后才清理其他中断任务，
避免先退款本可恢复的完整结果。恢复期间禁止派发；全部启动清理完成并开始
监听后才恢复队列。已退款任务找回结果仍保留 failed/退款，标注迟到可领取，
不补扣、不复活取消的余图、不释放别的任务槽。

缺失、半写、损坏或身份不符的结果不记成功，保留证据；旧 running 通过现有
未知结果流程幂等退款，损耗按 F03 分资源记录。没有对应描述的旧孤儿文件
不自动认领。手动清请求日志跳过待恢复任务；默认历史裁剪也保留它们。
生产既有 `NO_AUTO_DELETE=true` 继续保护全部记录/文件，500 条默认缓存值
不会删除共享结果，历史退出内存后仍可通过冷查询签名领取。

新增 0009 仅为 jobs.data 中的 resultPending 建部分索引，不新增任务字段
影子列或第二套存储框架。查询只返回分页 ID，保留冷历史和原排序；迁移仍
受既有 hash 检查约束，不能回写旧迁移。

## 正常退出

SIGTERM/SIGINT 先停止接收新请求和新派发，等待已开始的派发事务及在途
执行、正在进行的余额/核对任务、存储队列和已有 HTTP 响应。这样不会因为
结算先完成就截断仍在发送的图片。`SHUTDOWN_GRACE_MS` 默认 30000，合法
正数最多 600000；后台 SSE 等长连接也受同一总宽限约束。

宽限到期退出，持久任务和文件证据保留给下次启动恢复。强杀和进程异常不
依赖退出回调。systemd 的停止超时须留出应用宽限及退出余量；F11/D01 实际
拆服务和部署时再核验。不能靠启多个调度进程来实现共享账本的滚动重启。

## 同步、性能与保证边界

写连接由 WAL/NORMAL 改为 WAL/FULL。FULL 在每次事务提交时同步 WAL，
用于提高断电后提交的持久性；NORMAL 的事务一致性不等于每次提交均耐受
断电。[SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)

文件同步与目录项同步分别执行，新建 images 目录时也同步其父目录。
文件 fsync 本身不足以保证 rename 的目录项落盘；实际行为仍依赖操作系统、
文件系统和设备兑现同步请求。[Node FileHandle.sync](https://nodejs.org/docs/latest-v22.x/api/fs.html#filehandlesync)、[Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html)

Windows 无此实现可用的可移植目录 fsync，明确跳过该步骤；Windows 检查是
进程崩溃/功能验收，不是 Linux 目录持久性保证。SIGKILL 检查也不等于拔电、
硬盘故障或宿主机崩溃实验。上游已消费而完整结果尚未到达时仍无法凭空找回。

本地合成微基准每模式三轮，各预热 10 次、采样 200 次；一次事务更新账户、
成员、任务、账本及小型设置。表中为三轮分位值的中位数，单位 ms：

| 环境 | NORMAL P50 / P95 | FULL P50 / P95 |
| --- | ---: | ---: |
| Windows Node 22.22.2，本机磁盘 | 0.192 / 0.735 | 0.947 / 1.711 |
| Linux Node 22.23.3，Docker 挂载 Windows 磁盘，2 CPU | 11.091 / 14.640 | 12.816 / 17.633 |

20 次 1 MiB 合成二进制发布，Windows P50/P95 为 3.536/5.156 ms，Linux
为 29.433/34.706 ms；前者不含目录同步，后者包含。没有用 tmpfs 作为这个
磁盘测量的数据卷。脚本和原始结果保留在 `_private/f10-durability-*`。
这不是 bob 原生 Linux 文件系统、生产账本规模或端到端生图性能；D01 在
部署副本复测，不能拿本表代替生产延迟承诺。

## 验证记录

最终 Windows 全套 411 项：408 通过、3 项明确跳过 Linux 专属的目录同步、
符号链接和真实 SIGTERM，98 文件语法通过。实际子进程在描述提交后、半写、
文件 fsync 后、rename 后、目录 fsync 后、最终 SQL 提交后但响应前强杀，
每个场景再启动两次核对：原模拟上游只请求一次，完整结果保持原 imageId
并能签名领取；缺失、半写及同长篡改不记成功，原预扣只退款一次。

另覆盖已退款 Vibe 的完整 part 恢复、Native 两图恢复后下一张保持十秒间隔、
正常 SIGTERM 与 100ms 超宽限、503 份结果在 500 热缓存上限下冷查询/签名
领取、描述提交失败零文件、最终 SQL 失败文件保留、跨尝试/成员/结果 ID
冲突，以及不可恢复冷任务不重新热载。测试故障开关只存在于 test-only
preload，生产入口没有注入开关。

最终 Linux 镜像 `novelai-shared-gateway:f10-check`
（sha256:60e77cabf01f999b259f061f8314d2998a0dd8b8799fd2055a6afacc8c9d825a）
在 UID 1000、断网、只读根目录和独立临时数据下通过十迁移、FULL、冷批次/
载荷预算/幂等映射/SQLite 完整性/HTTP 启动；文件、待恢复存储、真实故障
恢复、迟到结算与刷新退出共 45 项全部通过，包括上述 Windows 跳过项。
容器里的故障注入使用临时卷，磁盘微基准另用前述磁盘挂载，两者用途不同。
