## 条件矩阵与缓存含义

目标为 3 个角色 × 2 个视口 × 2 种 HTTP 缓存设置 × 5 次，共 **60 条**。

| 条件 | 固定设置 |
| --- | --- |
| 角色 | anonymous（匿名登录页）、member（普通成员页）、owner（控制台） |
| 桌面 | 实际1440×900，DPR记录为1.0000000298023224（约1） |
| 移动视口 | 实际390×844，同一DPR；表示该视口的浏览器模拟，不代表真实手机硬件 |
| CPU | CDP 4× slowdown |
| 网络 | 延迟 150 ms；下行 200000 B/s（1.6 Mbit/s），上行 93750 B/s（0.75 Mbit/s） |
| 浏览器 | Chrome 155 / Windows 的当前用户 profile，保留已有扩展；不是全新 profile 或隔离性能实验 |
| 页面状态 | 页面保持可见；逐角色切换会话，点击同源链接进入，再按固定条件测量 |
| 重复 | 每个角色/视口/缓存组合各 5 次，不拿其他组合的记录补数 |

“冷”仅指 **HTTP 缓存禁用**，“热”仅指 **HTTP 缓存启用**；没有清除 DNS、连接池或操作系统缓存，也没有重启后端或清空 Discord 资格缓存。静态资源当前使用 `Cache-Control: no-store`；本轮缓存启用的80次静态请求全部仍完整传输，详见下表，不称为缓存命中。

这些条件用于固定本轮比较边界，不消除浏览器扩展、宿主机负载、连接复用、采样顺序和模拟限速的影响。每组只有 5 次，汇总以中位数和范围为主，不将其称为生产用户分位数、SLA 或真实移动设备性能。150 ms 是 CDP 配置参数，不是实测 RTT；TTFB 仍按浏览器实际记录报告。

浏览器工具的页面观察/代码注入本身也可能影响主线程和绘制呈现。本轮统一采用“注入 observer 后立即返回 → 读取一次页面状态 → 下一次工具调用读取结果”，没有用阻塞的 awaitPromise 等待绘制。尽管固定了流程，仍不能将这里约3–5秒的绘制/内容时间全部归因于业务脚本，或直接套用到生产用户。

## 指标、DOM 判定与观察窗口

浏览器采集函数保存在 `_private/browser-baseline-probes.js` 的 `startProbe/readProbe`。通过 CDP 读取 Navigation/Resource Timing，并使用 `buffered: true` 的 PerformanceObserver 收集 LCP 候选、布局位移和长任务。所有时间相对本次 navigation 的 time origin，以毫秒计；实际采集开始时间 `probeStart` 保留在每条记录中。

| 指标 | 定义与限制 |
| --- | --- |
| HTML TTFB | `navigation.responseStart`，包含从导航开始到首字节的时间，不等同纯后端执行耗时 |
| FCP | 浏览器 `first-contentful-paint.startTime`；与业务数据完成时间分开展示 |
| LCP（观察窗内） | 截止 `cutoff` 的最后一个有效 LCP 候选时间；不是整个页面生命周期的最终用户指标 |
| 关键 DOM ready | 下表条件第一次被探针发现满足的时间；是内容状态检查，不称为 TTI 或精确可交互时间。owner 这里只代表顶部概览，不代表默认用量页全部完成 |
| secondary DOM ready | owner 还要求统计表有子行；其余角色沿用关键 DOM 条件 |
| 长任务 | 仅汇总观察窗中的已记录任务，报告次数和时长；保留原始 start/duration，跨截止点的时长须明确窗口交集，不将长任务总时长称为 TBT |
| 资源瀑布 | 只保留同源 pathname、类型、起止时间、状态和传输/编码/解码大小，不保存完整 URL 查询串、请求头、Cookie 或响应体 |

DOM 判定与现有探针保持一致：

| 角色 | 关键 DOM 条件 | secondary 条件 |
| --- | --- | --- |
| anonymous | 已观察到 `/api/member/me` 资源完成，`login`、`discordForm` 非 hidden，`discordLogin` 未 disabled | 同左。未登录 `/me` 的 401 是预期行为，不算后端故障 |
| member | `account` 非 hidden，`jobs` 已有子行 | 同左 |
| owner | `dashboard` 非 hidden，`connectedHint` 文本以“已连接”开头 | `usageRows` 已有子行 |

owner 初始化为 `refresh().then(()=>tab('usagePanel'))`，默认进入用量页；secondary 才覆盖该默认用量表。不能因为静态 HTML 初始 hidden，就将统计视为默认不可见或无用请求。

若注入探针时条件已经成立，记录 `upper=true`：真实 DOM ready 发生在观测之前，`criticalMs` 只能作为该时刻的上界。即使 `upper=false`，仍有 requestAnimationFrame 检查粒度，不能把探针时间当作无误差时间戳。`probeStart/criticalMs/secondaryMs/upper` 均保留；汇总会注明上界样本数，不把上界与 FCP 混成一个“首屏时间”。

每条记录的观察窗从导航开始，到 `cutoff = max(secondaryMs, fcpMs) + 1000`。LCP、布局位移、长任务均限定在这个窗口；晚于窗口的轮询更新不参与首屏汇总。需要核对 `complete=true`、观察已到截止时刻、关键 DOM/secondary/FCP/LCP 有有效值以及页面可见；不完整或后台样本不能填成 0。SSE 长连接不使用 network-idle 判定完成，其请求可能没有已完成的 Resource Timing 条目。

### CLS 重新计算口径

采用标准的**最大 session window**：相邻有效位移间隔小于 1 秒、单窗口跨度小于 5 秒时累加到同一窗口；否则开启新窗口，最终取各窗口分数的最大值。不能把全部位移分数直接相加。该规则及用户输入位移排除依据 [Chrome/web.dev 的 CLS 定义](https://web.dev/articles/cls)。

探针已在采集时排除 `hadRecentInput=true`，原始 JSON 的 `shifts` 保留其余位移的 start/value。核算先按本条记录 `cutoff` 筛选并排序，再按上述规则重新计算，不依赖采集中的旧累加 `cls` 字段，也不覆写原始位移记录。10条 owner 桌面记录由旧累加约0.03282修正为最大窗口约0.02813；其余50条相同。表中称为“观察窗 CLS”，不冒充全生命周期现场 Core Web Vitals。
