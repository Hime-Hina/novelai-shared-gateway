# 结果持久性与崩溃恢复（F10）

适用范围是通过统一共享队列受理的网页、Native、direct、OpenAI、生图、
放大和 Vibe 编码。一个任务只有一次上游尝试；恢复不再次请求 NAI。已停用
的官方 Key 独立缓存路径及旧 inline 图片搬移不据此宣称同样的尝试恢复保证。

本页前半部分描述当前重构分支的持久性边界；文末 F10 数字是既有验证记录，不能当作本轮事件重构已经完成生产升级的证据。运行版本和发布授权以[正式发布记录](../operations/production-release.md)为准。

## 事件权威与启动

本轮未发布关系候选的普通入口已改用唯一 `gateway-runtime.ts` 关系装配，保留 `startGateway/handleGatewayRequest`。启动只接受现存、当前 DDL/hash/writer/reducer 且完整 cut 为 ready 的数据库；不会在线开账、迁移或修补 ready。先在 DATA_DIR 的独占私有临时副本恢复 DB/WAL/journal 并调用现格式、ready/FK 与配置 owner，再核原文件及 sidecar 的 64KiB 流式 SHA256/BigInt 身份未变，才首次实际打开原库并复核。无效源不由 SQLite 打开，原 DB/sidecar 字节保持；预检确有 O(DB+WAL+journal) 临时磁盘与 IO 成本。DATA_DIR 必须具受保护 ACL，启动源必须单 writer 且静止；前后复核不声称消除不合作外部写入者的全部 TOCTOU。

随后原结果 owner 恢复 prepared 文件，原执行器准备中断任务；只有实际 listen 成功并再次确认当前 ready，才激活原队列和唯一账户观察循环。端口占用、恢复故障和监听期间 ready 失效都不派发新任务。新受理在正文/缓存/认证 IO 后的原事务内核同一 queue 当前 phase，旧合法回执先于该新决定门禁。关闭停止调度并等待真实生成控制与 quota 原网络 Promise；drained 仅唤醒，领取 owner 先冷读终态，再从当前 stopped phase 结束非终态等待，晚注册同样适用。最后等 HTTP handler 和真实 response finish/close，清理 idle keep-alive 并等 server close，再关数据库，不能以强退 exit0 代替。关闭不会取消 queued 业务或伪造退款，重启仍按原事实执行。限时签名采用单进程密钥，重启失效。

下文 `event_commits`、`JsonStore`、旧开账/inline 升级及 writer4 的说明属于旧格式的独立解释工具和历史 F10，不能据此启动新入口自动转换。新格式的完整提交、保护内容、选定私有快照与唯一 ready installer 见[离线恢复](../operations/relational-recovery.md)，同候选发布物与切换验收仍未完成。

### 旧格式解释与历史启动

账务和任务生命周期由 `domain_events` 的业务事实重建，`event_commits` 保存整笔提交的顺序与回执。钱包、预留、任务、冷结算和免费次数是同一 SQLite 事务内维护的投影；事件写入或投影失败会一起回滚。读路径不以查询为由补发恢复额度、初始化运营账或更新钱包。

唯一执行器的启动顺序是：迁移并加载 SQLite；在首次领域写入前完成旧库 opening；创建结果目录，恢复已描述的完整产物，再清理其他中断/过期任务；完成旧 inline 图片迁移、配置应用等启动工作；最后 `enableEventAuthority()` 核对事件与关键投影、写入权威版本标记。只有切换成功，HTTP 才开始监听，队列才允许派发。投影、权威版本或迁移历史不匹配，以及仍未处置的 running 尝试会阻止切换，不能通过忽略核对结果继续写账本。

Opening 保存导入时确实存在的成员/分组、账户与额度、运营账、预留、任务与产物关联、冷幂等/结算、免费使用凭据和队列游标。旧 ledger 以 `LegacyFactRecorded` 留存；旧输入和私有字段移入受保护记录，并在事件中保存引用/摘要。导入按块记录来源摘要，重复执行不重建同一块，半途失败可续跑；已导入块对应的来源变化会被拒绝。Opening 不是补造过去的逐次恢复、派发或官方实耗，也不调用上游补齐没有保存的历史。

首次开账的维护等待应覆盖旧库导入、结果恢复、投影核对及健康验收，先用同规模隔离副本实测；本轮规模与耗时见[性能记录](../history/refactor-performance-evidence.md)。执行器完成这些步骤后才监听，systemd 的 `Type=simple` 显示 active 不等于 HTTP 已就绪。Compose 当前探针只有 30 秒启动宽限，随后每 30 秒探测、三次失败标 unhealthy，可能先于大库开账完成；仓库未配置因此终止进程，外部自动化的等待预算仍须在升级前按实测窗口核对。保持维护入口关闭，确认进程和日志没有失败，再等待执行器鉴权健康检查及账本核对成功后启动网页、恢复入口；不能把网页 45 秒请求限制或小库 smoke 的 15 秒当作升级超时。需要沿用旧 owner 会话时，先按[切换顺序](../operations/production-release.md#切换顺序)完成五分钟内的凭据导入，再启动开账。

## 共同备份边界与离线重放

事件文件单独存在不足以恢复服务。应从同一一致性 SQLite backup 保留完整数据库，并同时保留其匹配的产物与受保护配置：

| 类别         | 必须保留的事实/内容                                                                                        |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| 事件与版本   | `domain_events`、`event_commits`、opening/historyId、权威/迁移元数据；投影和游标可校验重建                 |
| 原输入       | `generation_requests`、`generation_contexts` 中的完整参数、首次规范化上下文和确认；事件只存引用/摘要       |
| 旧产物与诊断 | `artifact_inputs` 中已有的 inline 字节/提示词，`generation_diagnostics` 中的私有错误详情；各自保留摘要校验 |
| 认证与部署   | 成员认证、PST、会话、相关配置/签名密钥，以及必要 R2/PikPak 访问配置，均作为受保护数据保存，不混入公开事件  |
| 产物字节     | 本地 images 和仍需恢复的完整 `.part`，以及独立保存的 R2/PikPak 对象清单、位置、长度和 SHA-256              |

在线备份必须通过 SQLite backup 纳入已提交 WAL；不能只复制正在写入的主文件。现有 `backup-production.py` 的日常业务快照明确标记 `imagesIncluded:false`，不能据此声称图片字节也在该包内。恢复还要独立保留本地图片、R2/PikPak 凭据及外部对象清单，并核对各位置的文件与清单，缺失字节不能由事件重新生成。部署配置、密码、输入和诊断均属于私有备份。

仓库入口为 `scripts/replay-events.mjs`；发布包入口为 `executor/.output/server/node_modules/novelai-shared-gateway/scripts/replay-events.mjs`。使用同包固定 Node，源为只读一致性备份，目标为新的隔离数据库；续跑只使用同一 historyId 的既有目标：

当前 writer/minimumWriter 与 reducer 为 4，事件封套仍为 v1；v1/v2/v3 权威备份必须先复制到隔离目录，用当前包的 `JsonStore.init()` 完成存储版本升级并关闭，再以该升级副本作为只读重放源；不要启动网关、联网派发或改写原始备份。升级会在同一事务中，把旧查询行中确实存在但旧事件未保存的上游时间/HTTP 状态追加为 `ResponseEvidenceRecorded`，保留 `legacy-query-projection` 来源及来源行摘要；旧事件不重写，缺失字段保持未知，不用派发授权时间或升级时间补造。升级失败回滚，成功后要求当前 writer/reducer。重放入口在创建或写入目标之前拒绝旧版源并提示此步骤，避免把仍可恢复的查询证据静默丢弃；已升级源中的旧事件仍可正常重放。

当前 writer 的 `ArtifactPrepared`、`JobFailed`、`JobCompleted` 和 `LateResultRecovered` 写入类型要求显式提供 `response`。生命周期命令继续用同一证据 helper 表达未知时间或未发送，历史事件读取允许缺字段，版本无需变更。

```sh
node scripts/replay-events.mjs --source=/private/backup/library.sqlite --target=/private/rebuild/library.sqlite --max-commits=100
node scripts/replay-events.mjs --source=/private/backup/library.sqlite --target=/private/rebuild/library.sqlite
```

参数采用 `--name=value`。`--max-commits=N` 在整笔提交边界暂停，重复执行从已提交游标继续；完成后再跑为零新增。`--through=COMMIT` 可指定业务事件截止游标，但受保护输入与认证来自所选源备份，并不构成该历史时点的完整服务快照。源必须有完整 opening；未知事件/schema/金额版本、不同来源历史或无效顺序被拒绝。CLI 只复制受保护事实并重建数据库投影，不请求 NAI、不重新派发、不下载 R2、不复制产物文件，也不替换运行中的库。

恢复验收须检查完整性、重放游标、余额/冷结算、任务与产物归属、受保护摘要及实际内容可领取；随后由唯一执行器执行启动恢复和权威核对。不能把分段未完成的目标上线。目标路径、文件/R2/PikPak 恢复和切换授权仍按[发布记录](../operations/production-release.md)执行。

PikPak 上传确认并持久记录后才删除 R2 原件；上传后不立即回读，领取时才限量解压并校验原长度和 SHA-256。旧快照若仅有已验证 R2 描述符，可配置原 PikPak 目录与凭据后按原 SHA-256 回退读取；错误目录、缺失或损坏不能视为恢复成功。完整恢复须实际领取冷图，PikPak 不是数据库备份目的地。

同键回执和缓存复用依据已确认的持久产物来源。缺少存储配置或归档目录不匹配时，实际读取返回 503，仍可领取原任务回执并复用原图引用。

## 历史退休和旧 writer

清理终态任务通过 `retireJobHistory()` 按不超过 200 条的批次提交 `JobHistoryRetired`。活动任务、带 resultPending 或尚未结案 generationReview 的任务不能退休；重放会保留退休事实并删除相应 jobs 投影，不会重新出现旧任务。已完成 child 可在其他 child 仍活动时退休，但原 parent、完整 child 集合、输入和冷结算保留，后续派发仍把已退休 child 的费用计入原批次上限。事件、冷结算和幂等防重记录仍保留，旧键找不到原目标时返回 410，不能再生成一次。当前不会随退休自动删除受保护输入、产物输入或诊断；图片字节仍按独立产物保存规则处理，不能把日志退休当作完整数据删除。

`event_authority` 标记要求兼容 writer，迁移器同时校验每个已应用 SQL 的 hash；当前实现拒绝未知的更高 writer/迁移版本。旧发布不因此自动获得新语义，不能删除标记或降级迁移文件来强行打开新库。启动恢复、退款、补充事实和归档均可能在监听前产生写入；只有确认无必须保留的新写入或外部存储变更时，才能整体恢复升级前完整备份。发生新事件写入后，不得用旧快照覆盖账本实现回退；应保留原事实，在隔离副本验证兼容读取或修复后再按授权切换。当前仍只允许一个执行器写同一库。

## 提交与恢复顺序

1. 检查任务、成员、账户、尝试和原结算凭据，在独立 SQLite 事务中提交
   `ArtifactPrepared` 及其 `job.resultPending` 投影：attemptId、imageId、file、operation、mimeType、byteLength、sha256。
   同时保留上游时间与状态证据，描述提交失败时不开始写文件。
2. 在现有串行写流程内，校验内容与描述一致，以 `wx`、0600 创建同目录
   `${file}.part`，完整写入、文件 fsync、rename 为最终文件、目录 fsync。
   已有同内容完整文件可复用；路径、长度、SHA-256 或格式不符则保留原文件
   和描述并报错，不覆盖、删除或猜测它属于哪个任务。
3. 同一领域提交写入产物发布、任务终态、扣费结算或迟到结果、冷却与批次
   下一张激活，并删除 resultPending。失败回滚保留此前已提交的描述和文件。
   重试沿用原 imageId，重复完成不创建第二份结果，也不重复扣退。

图片继续使用 F07 的 PNG/JPEG/WebP 校验、64 MiB、16384 边长及原像素限制。
Vibe 编码作为非空 opaque 二进制处理，以原媒体类型、长度和 SHA-256 验证，
不把它送进图片解码器。新结果记录保留 operation、byteLength、sha256。

启动先创建图片目录，再从部分索引按 ID 分页查询待恢复任务，逐条验证；
完整 `.part` 可补发布，完整最终文件可直接复用。随后才清理其他中断任务，
避免先退款本可恢复的完整结果。恢复期间禁止派发；全部启动清理完成并开始
监听后才恢复队列。已退款任务找回结果仍保留 failed/退款，标注迟到可领取，
不补扣、不复活取消的余图、不释放别的任务槽。

缺失、半写、损坏或身份不符的结果不记成功，保留证据；旧 running 通过现有
未知结果流程幂等退款，损耗按 F03 分资源记录。没有对应描述的旧孤儿文件
不自动认领。手动清请求日志跳过待恢复任务；默认历史裁剪也保留它们。
配置 `NO_AUTO_DELETE=true` 时继续保护全部记录/文件，500 条默认缓存值
不会删除共享结果，历史退出内存后仍可通过冷查询签名领取。

F10 使用的 0009 仅为 jobs.data 中的 resultPending 建部分索引，不新增任务字段
影子列或第二套存储框架。事件及受保护输入/诊断表由随后追加的迁移建立。
待恢复查询只返回分页 ID，保留冷历史和原排序；所有迁移仍受 hash 检查约束，
不能回写旧迁移，发布包必须保留完整 SQL/journal。

## 正常退出

SIGTERM/SIGINT 先停止接收新请求和新派发，等待已开始的派发事务及在途
执行、正在进行的余额/核对任务、存储队列和已有 HTTP 响应。这样不会因为
结算先完成就截断仍在发送的图片。`SHUTDOWN_GRACE_MS` 默认 30000，合法
正数最多 600000。成员状态和任务预览 SSE 在开始关闭时正常 EOF，不发会话
失效通知；在途生成响应仍有同一总宽限用于完成交付。

宽限到期退出，持久任务和文件证据保留给下次启动恢复。强杀和进程异常不
依赖退出回调。systemd 的停止超时须留出应用宽限及退出余量；F11/D01 实际
拆服务和部署时再核验。不能靠启多个调度进程来实现共享账本的滚动重启。

新格式离线 ready 安装要求受保护字节闭包已恢复：待恢复的准备结果由生成 owner 核验原描述、归属和输入，再只读核验存在的最终文件及 `.part`。至少一份完整且不存在原文件 owner 认定的冲突，才能安装；两者皆缺、半写或损坏时拒绝，保留原准备与责任，不自动发布、退款或把后续启动恢复当作本次成功。完整 final/part 可通过核对，但仍保留原运行中或未决状态，之后才由原恢复命令提交完成。该安装规则与实际验证见[数据库计划 9.23](../plans/database-model-redesign.md#923-50-离线完整核对与-ready-安装契约)。

## 同步、性能与保证边界

写连接由 WAL/NORMAL 改为 WAL/FULL。FULL 在每次事务提交时同步 WAL，
用于提高断电后提交的持久性；NORMAL 的事务一致性不等于每次提交均耐受
断电。[SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)

文件同步与目录项同步分别执行，新建 images 目录时也同步其父目录。
文件 fsync 本身不足以保证 rename 的目录项落盘；实际行为仍依赖操作系统、
文件系统和设备兑现同步请求。[Node FileHandle.sync](https://nodejs.org/docs/latest-v22.x/api/fs.html#filehandlesync)、[Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html)

Windows 无此实现可用的可移植目录 fsync，明确跳过该步骤；Windows 检查是
进程崩溃/功能验收，不是 Linux 目录持久性保证。SIGKILL 检查也不等于拔电、
硬盘故障或宿主机崩溃实验。上游已消费而完整结果尚未到达时仍无法凭空找回。

本地合成微基准每模式三轮，各预热 10 次、采样 200 次；一次事务更新账户、
成员、任务、账本及小型设置。表中为三轮分位值的中位数，单位 ms：

| 环境                                                | NORMAL P50 / P95 |  FULL P50 / P95 |
| --------------------------------------------------- | ---------------: | --------------: |
| Windows Node 22.22.2，本机磁盘                      |    0.192 / 0.735 |   0.947 / 1.711 |
| Linux Node 22.23.3，Docker 挂载 Windows 磁盘，2 CPU |  11.091 / 14.640 | 12.816 / 17.633 |

20 次 1 MiB 合成二进制发布，Windows P50/P95 为 3.536/5.156 ms，Linux
为 29.433/34.706 ms；前者不含目录同步，后者包含。没有用 tmpfs 作为这个
磁盘测量的数据卷。脚本和原始结果保留在 `_private/f10-durability-*`。
这不是 bob 原生 Linux 文件系统、生产账本规模或端到端生图性能；D01 在
部署副本复测，不能拿本表代替生产延迟承诺。

## 既有 F10 验证记录

最终 Windows 全套 411 项：408 通过、3 项明确跳过 Linux 专属的目录同步、
符号链接和真实 SIGTERM，98 文件语法通过。实际子进程在描述提交后、半写、
文件 fsync 后、rename 后、目录 fsync 后、最终 SQL 提交后但响应前强杀，
每个场景再启动两次核对：原模拟上游只请求一次，完整结果保持原 imageId
并能签名领取；缺失、半写及同长篡改不记成功，原预扣只退款一次。

另覆盖已退款 Vibe 的完整 part 恢复、Native 两图恢复后下一张保持十秒间隔、
