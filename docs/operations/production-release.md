恢复时先执行 `--verify`，将 `data/` 复制到独立恢复目录，重新校验再按上节停机替换；
`config/` 与 `systemd/` 按目标版本恢复到对应路径。不要把快照图片或数据库硬链接到
将投入运行的恢复目录，否则后续原地修改会污染备份。备份权限与原数据目录的服务用户
权限不同，正式恢复前须重新设置 `nai-gateway` 的归属与访问权限。
新关系库应按[关系恢复工具](relational-recovery.md)将选定快照的完整业务和当前私有状态
恢复到独立目标，经唯一 installer 核验后发布；不能手工设置 `ready`。
`--verify` 对既有全图片旧备份仍核对原图片或原归档凭据；显式旧清理也保留原保护，
两者不构成新关系副本的回收入口。新副本释放仍待归档引用权威与独立验收，本次不改变 D8 留存期限。

执行器读取 `/etc/novelai-shared-gateway/r2.env` 中四个 `R2_*` 字段（见 `.env.example`）。
使用 Standard 私有桶，凭据仅授予该桶对象读写；不启用公开访问。空闲时逐张处理生成超过
24 小时的 PNG/JPEG/WebP，跳过 mock、活动及待恢复结果。先持久预留容量，条件 PUT 后
GET 回读验证完整字节及 SHA-256，再持久化 R2 凭据，最后移除本地副本；失败保留副本并
延迟一小时重试。不重编码图片，原图内嵌参数不变，数据库生成参数同样保留。
历史查看、下载与缓存命中沿用原鉴权和签名 URL，由执行器代理读取并再次校验原图。

R2 以 **8,550,000,000 B** 为热图片转冷水位，不设项目总容量硬上限。
每日业务快照压缩后使用独立随机 32 字节密钥做 AES-256-GCM 加密，再存入同桶 `backups/`；
备份流式处理，不受单份 50 MiB、图片 64 MiB 或备份总量 500 MB 的旧项目限制；单次 PUT 上限为 5 GiB 减 5 MiB，图片本身仍限 64 MiB。
新包成功回读、解密比对并写入回执后，云端轮换按不同对象 key 选出最近七份。开始删除前逐份校验拟保留对象的长度、SHA-256 和 GCM，复用本轮新包的验证结果。常规轮换额外回读六份旧包，回填旧日期时最多七份，逐份复用同一组临时文件。
任一拟保留对象校验失败时整次删除不启动，允许云端暂时保留超过七份。脚本报告轮换失败，保留新回执、本地新快照和旧备份。本地仅在远端步骤成功后轮换。
密钥为 `/etc/novelai-shared-gateway/backup-encryption.key`，必须另外保留离机副本；
仅有 R2 对象而丢失密钥无法恢复。配置和密钥只在服务器受保护文件及加密归档中保存。

## 可选 PikPak 冷归档

PikPak Premium 的[当前 WebDAV 文档](https://mypikpak.com/en-US/help-center/connected_apps/webdav/how_to)
已支持上传及文件管理。执行器通过 `webdav` 客户端连接；在现有受保护的
`/etc/novelai-shared-gateway/r2.env` 中添加 `.env.example` 的三个 `PIKPAK_WEBDAV_*` 字段，
无需新增 systemd 环境文件。URL 必须是 HTTPS 并指向预先创建的本站专用目录，不含凭据、查询参数
或片段。目录和凭据须保留，不能在转存后随意更换。Nuxt 不读取这些凭据。本机可另用 Git 忽略的
`.env.pikpak.local`，通过 Node 的 `--env-file` 显式加载。

沿用空闲时逐张归档：本站图片在 R2 的已用及预留总量达到热存储水位 **8,550,000,000 B**
时，优先迁移在 R2 存放最早的图片，降到阈值以下停止容量迁移；**在 R2 存放超过七天**的图片
不受容量条件限制。七天从 R2 `verifiedAt` 计算，不从生成时间计算。备份对象沿用原七份保留策略。

读取并校验 R2 原图后，使用 Node 内置 Brotli 最高级别 11 无损压缩，上传为归档目录下的
`<原图 SHA-256>.br`。原图内嵌参数和数据库参数保留。PNG/JPEG/WebP 已压缩，二次压缩收益可能很小，
小文件也可能略微增大。PikPak 实测忽略条件 PUT，因此使用内容哈希命名，重试只写入同一原图内容。

按用户选择，**上传后不下载回读校验**。上传成功且归档目录、上传时间等回执持久提交后才删除 R2
原件，再持久记录移除完成；容量在最后一步提交后才扣减。失败按图片延迟一小时重试；已持久确认上传
的重试不重复上传。超时或回执提交失败时保留 R2，允许重新上传同一内容。此策略无法在释放 R2 前发现
网盘静默损坏，服务端成功回执不等同于内容已验证。

成员查看、下载或命中缓存时才读取 PikPak，限量接收压缩数据、限量解压，再校验原图长度和 SHA-256。
沿用既有鉴权和签名 URL，不返回网盘地址或凭据。旧备份只要已有已验证的 R2 描述符，配置同一 PikPak
目录后便可凭原 SHA-256 找到冷图，不要求旧库带有新回执。恢复时必须提供当前 PikPak 凭据并运行支持
冷归档的版本；回退旧版前应下载解压已迁移原图，不能只切换程序链接。

管理资源区的账户实际已用量和总容量通过 PikPak Drive 的 `GET /drive/v1/about` 读取，
与本站归档原图规模分别展示。WebDAV 不提供容量配额，因此在同一受保护的 `r2.env` 中配置
`PIKPAK_API_TOKEN`，使用 PikPak「账户与安全 → 已连接的应用 → 个人访问令牌」创建的只读 PAT；
「读取文件」权限已实测足够。令牌仅交给执行器，不返回网页；不需要账户密码或新的客户端依赖。
接口使用 `quota.usage` 和 `quota.limit` 的字节值，按分钟异步缓存；请求失败保留上次统计及时间，
没有成功数据时显示未知，不阻塞管理页。PAT 按用户选择的有效期到期后需替换，创建及权限说明见
[PikPak 官方 FAQ](https://mypikpak.com/en-US/faq)。查询实现与归档接入同在 `server/storage/pikpak-storage.ts`。

WebDAV 使用[Connected Apps 传输额度](https://mypikpak.com/en-US/help-center/connected_apps/webdav/speed_limit)：
下载限额触发限速，上传额度耗尽则阻止后续上传。上传被拒时保留 R2 原件，不将失败视作已迁移。

`server/storage/pikpak-storage.ts`；相似策略调整在对应模块修改。
